# 0005. Auth: own server-side sessions; email+password in MVP, Google next

- **Status:** Accepted (owner, 2026-11-08)

## Context
The owner asked for the option that is most secure and simplest for students. Auth has two parts: **staying logged in** (the session mechanism) and **signing in** (the login method).

## Options: session mechanism
1. **Own server-side sessions stored in Postgres.** The session id goes in an `HttpOnly; Secure; SameSite=Lax` cookie. Sessions can be revoked instantly, no token is readable by JS, and no Redis is needed.
2. JWT bearer tokens. Stateless, but revocation is awkward and browser token storage is an XSS risk.
3. Managed provider (Supabase Auth / Clerk). No password code, but it brings vendor lock-in, pulls hosting toward that vendor, and adds a second identity system.

## Options: sign-in method
Email + password, "Continue with Google", magic link, passkeys. See the comparison table in the session notes recorded in `docs/superpowers/specs/2026-11-08-phase-1-foundation-design.md`.

## Decision
- **Sessions:** option 1. CSRF protection is applied to state-changing requests.
- **Sign-in:** the **MVP ships email + password**: argon2id hashing, minimum length, rate limiting, and an optional breached-password check, all decided in the Phase 2 plan. **"Continue with Google" is the first post-MVP auth feature.**
- **Phase 1 schema prepares for this:** `users.password_hash` is **nullable**, and a separate `auth_identities` table (provider + provider subject) exists so OAuth drops in without a migration of `users`.
- **Phase 1 builds no auth endpoints.** The sessions table, login/logout/register, and CSRF arrive in Phase 2.

## Consequences
We own password reset and email verification. These are deferred: the reset email isn't needed for the MVP loop. No date-of-birth column until the privacy/age decision (planning doc §5 #7, P2).
